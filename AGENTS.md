# Grok2API Operations Guide for AI Agents

This guide describes the deployment pattern and safety boundaries around the
Grok2API Quality Guard and egress services. A checked-out repository is not a
production runtime: deployment configuration, state volumes, proxy lists,
account bindings, and credentials must remain outside version control.

## Required Reading

Before investigating or changing Quality Guard, egress-node health, sticky IP
rotation, or TTFT account ranking, read these files in order:

1. `docs/QUALITY_GUARD.md` - authoritative implementation and operations reference
   for the deployed sidecar.
2. `docs/EGRESS.md` - egress topology and proxy-chain context.
3. `docs/RECOMMENDED_DEPLOYMENT.md` - recommended residential/Resin to Mihomo
   to Grok2API/Guard deployment flow.
4. `docs/LOCAL_PATCHES.md` - local behavior relative to upstream Grok2API.
5. `docker-compose.yml` and `config.yaml` - declared deployment configuration.
6. `tools/egress-quality-guard/quality_guard.py` - final source of truth for
   behavior when documentation and implementation disagree.

Values labelled as production snapshots in documentation are historical. Read
the current runtime state before drawing conclusions:

- the deployed sidecar's `/var/lib/grok2api-quality-guard/runtime-config.json`
- the deployed sidecar's `/var/lib/grok2api-quality-guard/bootstrap.json`
- the deployed sidecar's `/var/lib/grok2api-quality-guard/state.json`
- the running container environment, without printing secret values

## Configuration Ownership

Quality Guard configuration is layered. Do not assume editing one file changes
the running process:

- `runtime-config.json` hot-reloads only the exact runtime schema documented in
  `docs/QUALITY_GUARD.md`.
- `bootstrap.json` is generated by Grok2API from `config.yaml`; most bootstrap
  fields and `qualityGuard.enabled` are read when the sidecar starts.
- `RANK_*`, Admin credentials, and connection settings come from Compose/env
  and are read when the sidecar starts.

Always report which layer supplies the effective value. Confirm with
`state.json.guard` after a change.

## Safety Boundary

Default to read-only inspection. A request to "look", "check", "review", or
"diagnose" does not authorize edits, container recreation, node enable/disable,
sticky rotation, account reassignment, or state-file mutation.

Before an authorized runtime change:

1. Explain the exact affected component and whether it can isolate nodes,
   rotate an exit IP, or move accounts.
2. Back up the relevant configuration and state.
3. Validate the candidate configuration without printing credentials.
4. Restart only the required service. Do not restart `grok2api` when a sidecar
   restart is sufficient.
5. Verify container health, effective state, and recent structured events.

Do not edit `state.json` directly unless the user explicitly authorizes a
recovery operation and the ownership semantics in `docs/QUALITY_GUARD.md` have been
checked. With `fail_closed=true`, manually enabling a node still owned through
`disabled_by_guard` may cause the Guard to disable it again and require a
recovery probe.

## Secrets

Never print, copy into chat, commit, or use as fixtures:

- Admin passwords and access tokens
- `internal_token` or `rotation_token`
- proxy credentials and provider URLs containing userinfo
- account IDs paired with credentials or session material
- complete `config.yaml`, `quality-guard.env`, container environments,
  `bootstrap.json`, or credential files

When checking configuration, report only presence, source layer, permissions,
and redacted values. Keep host-specific Tailscale addresses and production node
inventories out of public documentation unless explicitly requested.

## Validation

For documentation-only changes, verify links, headings, commands, and agreement
with `tools/egress-quality-guard/quality_guard.py`; do not restart services.

For authorized Quality Guard code or Compose changes, validate before deploy:

```bash
python3 -m py_compile tools/egress-quality-guard/quality_guard.py
docker compose config --quiet
docker exec grok2api-egress-quality-guard \
  /usr/local/bin/grok2api-egress-quality-guard --check-config
```

After deployment, confirm `grok2api` remains healthy and inspect only recent,
redacted Quality Guard events. Remember that `RANK_DRY_RUN=false` performs real
account reassignment.
